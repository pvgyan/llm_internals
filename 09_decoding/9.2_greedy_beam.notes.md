##  束搜索（Beam Search）情况下的 KV Cache append

Q: 跟你上面讨论的 “KV cache 的追加（append）操作，也是自回归生成中 KV cache 更新的核心步骤“， 这里有个前提假设是 输出选择采用的是 贪心搜索（Greedy Search）， 但如果是  束搜索（Beam Search）这个问题就变得非常复杂了吧？（考虑每一步 都有 B条候选），能简单讲讲吧？ 另外， 像Qwen/llama 3/ Deepseek它们一般都用什么 输出选择策略？

A: 你抓到关键点了：**前面讲的“每步 append 一个 token 的 KV”是贪心 / 单条采样的前提**。一旦变成 Beam Search，就不是“1 条序列在生长”，而是“B 条候选序列各自在生长，并且每步还会被剪枝、重排、换父节点”。

---

## 一、贪心 / 单采样：KV cache 很简单

- 只有 1 条活序列
- 每步：算新 token 的 K/V → concat 到 `(B=1, n_heads, t, head_dim)`
- 下一步的 Q 只看这份 cache

这就是你前面理解的版本。

---

## 二、Beam Search：KV cache 变成“树 / 森林”

设 beam width = B。

第 t 步：
- 有 B 条候选序列
- 每条扩展 |V| 个下一 token → 得到 B×|V| 个候选
- 按累计 log prob 留前 B 条

问题来了：**留下来 B 条新序列，可能不是原来 B 条各生一个儿子，而是：**
- beam 0 生了 3 个好儿子
- beam 1 全被淘汰
- beam 2 生了 1 个
- beam 3 生了 1 个

所以新 beam 的“历史 KV”要从不同旧 beam 复制过来。

### 1. 朴素做法（能跑，但费显存）
每条 beam 独立存一份完整 KV cache：

```
K_cache: (B, n_heads, t, head_dim)
V_cache: (B, n_heads, t, head_dim)
```

每步剪枝后：
- 按 `surviving_beam_indices` 重排这 B 份 cache
- 新 token 的 K/V 再 append 进去

⚠️ 但前 t 个 token 的 KV 在 B 条 beam 里大量重复（共享 prompt、共享前缀），纯复制很浪费。

### 2. 工程做法：共享前缀 + Copy-on-Write
像 vLLM / SGLang / TensorRT-LLM 的做法：

- 用 **block table / physical blocks**
- 多条 beam 共享 prompt 和公共前缀的 KV block
- 只在某条 beam 开始“分叉”时，才分配新 block 写自己的 KV
- beam 被剪掉 → 引用计数 -1，计数为 0 的 block 才释放
- 剪枝重排 → 改的是“逻辑序列 → 物理 block”的映射表，不搬数据

可以想象成：

```
共享前缀 block: [prompt, tok1, tok2]
beam0: 共享 → tok3_a → tok4_a
beam1: 共享 → tok3_a → tok4_b
beam2: 共享 → tok3_b → ...
```

beam0 和 beam1 前 3 个 token 的 KV 是同一份物理内存。

### 3. 还有一个坑：beam 的“父节点”会变
第 t 步 beam 新序列 `new_beam_0` 可能来自旧 `beam_2` 的儿子。
所以 attention 读 KV 时要通过：

```
logical beam id  →  parent beam id  →  physical KV blocks
```

这就是 TensorRT-LLM 里 `cache_indirection` 的思路。

---

## 三、一句话对比

| 策略 | 活跃序列数 | KV cache 结构 | 每步动作 |
|---|---|---|---|
| Greedy | 1 | 单条线性序列 | append 1 个 token |
| Sampling | 1（或 N 条独立采样） | 每条独立 | 各 append 1 个 token |
| Beam Search | B | 前缀共享的树 / 森林 | expand B×V → 打分 → 剪到 B → 重排 KV 映射 |

所以你说得对：
> “append 一个增量”是贪心视角；Beam Search 里还要加一层“**KV 树的 fork / prune / reorder**”。

## 四、Qwen / LLaMA 3 / DeepSeek 一般用啥？

**聊天 / 助手类生成：几乎不用 beam search，用采样。**

典型默认：

- **LLaMA 3 Instruct**：`temperature=0.6, top_p=0.9`
- **Qwen3**：
  - 思考模式：`temperature=0.6, top_p=0.95`
  - 非思考模式：`temperature=0.7, top_p=0.8`
- **DeepSeek-V3 / R1**：
  - V3 类：`temperature≈0.6~0.7, top_p≈0.95`
  - R1 推理模型：温度通常固定/不开放采样参数，走确定性思考链路；R1-Distill 类常用 `temp=0.6, top_p=0.95, top_k=10` 这类配置
- 现代趋势：
  - `top_p` 仍在用
  - `min_p` 在 llama.cpp / DeepSeek-R1-Distill / Qwen3 生态里越来越常见
  - `temperature=0` = 贪心，只用于代码、抽取、评测
- **Beam Search 场景**：
  - 机器翻译
  - 代码合成（Codex / Code Llama 有时用）
  - 结构化解码、约束搜索
  - 不直接用于“闲聊 / 通用助手回答”

## 五、再浓缩一句

> 贪心：1 条线，append KV。
> 采样：N 条线，各 append KV。
> Beam：B 条线共享前缀，每步扩枝、剪枝、换爹，KV cache 用“块共享 + 引用计数”管。
> 主流对话模型：temperature + top_p（+ min_p），不是 beam。
